# Write content from a syllabus

The syllabus (made by `plan-syllabus`) decides **what** each lesson teaches: its outcome,
`topics` checklist, prerequisites and `kind`. This skill decides **how** it is written and
verified. Nothing goes module by module before the user has approved a pilot of every kind.

Read first: docs/DECISIONS.md ("Original content", "Lesson content format", "Content
pipeline"), the technology's `syllabus.yaml`, and the **exemplars** listed at the end of this
file (approved lessons of the same kind).

## 0. Where are we?

- Lessons live in `content/<technology>/lessons/<node id>/`; a node without a folder (or with
  `status: planned`) is not written yet. `pnpm content:check` lists the ready ones.
- **Pilot phase** while a kind used by the next lessons has no exemplar below. **Batch phase**
  when every kind needed has one.

## 1. Pilot (stop and wait)

1. Pick the earliest node (course order) of each kind the next module needs.
2. If the site cannot render that kind yet, build it first and tell the user: today `code`
   (Go only, see write-lesson), `terminal` and `state` (terminal sessions, `vis: areas` and
   `vis: graph`), `concept`, `compare` and `diagram` (text lessons, `vis: flow` / `vis: compare` /
   `vis: diagram`), `ui` (drawn mockups, `vis: ui`) and `code` for Markdown (the file and its
   rendered result) exist; `code` for YAML does not. A new kind or visual = a schema in `apps/site/src/lib/`, a
   branch in `Vis.astro` or a new stage component, CSS in `packages/theme`, and checks in
   `pnpm content:check`. Data-driven, never per-lesson JS; animations off under
   `prefers-reduced-motion`.
3. Write the pilot lessons (sections 2–5), verify them (section 6) and hand them to the user
   with the local URLs. **Stop.** Apply the feedback; when the user approves, add the lesson to
   "Exemplars" below, and move any new rule they gave into this file.

## 2. Brief (per lesson, before writing)

From the syllabus node: the **outcome** (the lesson must make the reader able to do exactly
that), the `topics` checklist (every item appears in a step, the text or the quiz), the
prerequisites (use only what earlier nodes taught; a later concept gets one clause or stays
out), `outOfScope` and `syntax` (e.g. `git switch`, not `checkout`). Then write down 3–5 ideas,
one per step, and one real-life context.

## 3. Writing rules

Follow the write-lesson skill, sections 2 (originality, real-life context that shows **why**,
USD for money, English in code and commands) and 3 (language and style, length, notes, 3–5
steps). Additionally:

- Contexts are everyday projects a beginner recognises (a trip plan, a portfolio site, a recipe
  book), one per lesson; file names and contents are English.
- The text may only cite what the recorded output really contains, and **never a commit
  hash** — hashes change when the session changes. Refer to the place instead ("the first line
  of the output").
- Explain what an output line means the first time it appears (`root-commit`, `A `, `??`).

## 4. Files of a terminal-session lesson (`terminal`, `state`)

```
content/<technology>/lessons/<id>/
  meta.yaml           subtitle, status: ready, level, source: original
  session.sh          the commands (the lesson's "code")
  steps.yaml          per step: optional `vis: areas`
  lesson.az.md        intro, `## Title {#step-id}` per step, optional outro
  quiz.az.yaml        5–10 questions
  takeaways.az.yaml   rules 3–6, practices 1–4
  session.json        GENERATED by pnpm content:run — never edit
  output.txt          GENERATED by pnpm content:run — never edit
```

### Files of a text lesson (`concept`, `compare`, `diagram`, `ui`)

No code pane and no session: the steps run full width one under another and each visual sits inside its step. No sticky panel (the user rejected it for this template).

```
content/<technology>/lessons/<id>/
  meta.yaml  lesson.az.md  quiz.az.yaml  takeaways.az.yaml
  steps.yaml          per step: optional hand-written `vis` (flow, compare, diagram or ui)
```

- `lesson.az.md` has 2–6 steps; no `session.sh` or `main.go` (the loader refuses them).
- `vis: { kind: flow, caption, arrows?, items: [{label, sub?, tone?}], note? }` — a row of boxes
  (versions, copies of a file, parts of a whole); `tone`: `good`, `bad`, `accent`.
- `vis: { kind: compare, caption, a: {title, sub?}, b: {title, sub?}, rows: [{aspect, a, b,
  better?}], note? }` — a `compare` lesson needs one in at least one step.
- `vis: { kind: diagram, caption, nodes: [{title, sub?, lines?, tone?}], links: [{right?, left?}],
  note? }` — 2–4 blocks side by side (stacked on a phone) with labelled arrows between them
  (`links` has one entry fewer than `nodes`): who sends what to whom (laptop ↔ GitHub, fork ↔
  upstream). A `diagram` lesson needs one in at least one step.
- `vis: { kind: ui, caption, url, tabs?: [{label, count?, active?, mark?}], main: [el], side?:
  [el], note? }` — a drawn mockup of a web page, not a screenshot. Elements (`type`): `heading`
  {text, sub?}, `text`, `field` {label, value?, placeholder?, hint?, state?: ok|error}, `select`,
  `button` {label, tone?: primary|default|danger}, `check` {label, sub?, checked?, radio?},
  `list` {items: [{title, sub?, icon?, meta?}]}, `code` {text, label?}, `box` {label, shape?}
  (a QR code, an avatar), `divider`, `row` {items} (side by side). `mark: "text"` on an element
  or tab puts a numbered badge on it and the text in the legend (at most 6). UI labels stay in
  English as on the real site and follow the official docs where they name them; say in the
  caption or the text that the screen is simplified. A `ui` lesson needs one in at least one
  step; usually every step has one (the screen is the point), like `state`.
- Strings take inline Markdown. Captions are not uppercased (they may name files and English terms).
- Keep it to one or two visuals per lesson (the user found busy visual pages confusing).
- Facts that are not checked by running a command (dates, who made what) must be well known and
  checked against the official documentation or the project's own history page.

### Files of a Markdown `code` lesson

The pane shows ONE Markdown file (e.g. `README.md`) split into steps; instead of a program's
output each step shows its lines rendered the way GitHub shows them ("Nəticə"), and "Tam nəticə"
renders the whole file.

```
content/<technology>/lessons/<id>/
  meta.yaml  lesson.az.md  quiz.az.yaml  takeaways.az.yaml
  README.md           the lesson's file; `<!-- @step id -->` / `<!-- @end -->` on their own lines
  steps.yaml          optional: hand-written `vis` per step
```

- Step ids in the file and in `lesson.az.md` are the same, in the same order (`content:check`).
- The preview is GitHub Flavored Markdown with GitHub alerts; images show as a placeholder with
  their alt text (no image files in the lesson); raw HTML stays text.
- Each step renders on its own, so a step should be a complete block (a whole list, a whole
  table).

### Session format

`session.sh`, one command per line:

- `#@step <id>` starts a step (ids: English kebab-case, stable once published), `#@end` closes
  one early. Blank lines and `# comments` are shown.
- `#@hide` hides the **next command** (it still runs): setup an earlier lesson taught
  (`mkdir`, `cd`, `git init -q`, creating files) so the visible commands are the lesson.
- A command ending in `#@fail` must fail (an error is the point); any other failure stops the run.
- `cd <dir>` is handled by the runner; no other multi-line or interactive commands (no editor,
  pager, `add -p`). For `rebase -i` and the like, script the editor in a hidden way
  (`GIT_SEQUENCE_EDITOR=...` in the command) and say in the text what a person would type.
- The sandbox: a fresh HOME shown as `/home/sam`, user Sam Lee <sam@example.com>, branch
  `main`, no colors, English messages, a clock that advances one minute per command — so the
  output is the same on every run. Each lesson starts from an empty HOME.

`steps.yaml`: `vis: areas` shows working directory / staging area / repository after the step,
recorded from the real repository (what changed since the previous step is highlighted).
`vis: graph` shows the commit graph the same way (commits newest on top, parents, branches,
tags, HEAD; new commits and moved refs highlighted); add `files: true` to also show each
commit's parent and its files (new / changed / same as in the parent) — for lessons about what
a commit holds, not for busy branch histories.
`state` lessons put a visual on every step — the visual is the point; `terminal` lessons add one
where the state is not obvious from the output.

## 5. Quiz and takeaways

- 5–10 questions, mostly "Bu komandalardan sonra nə çap olunur?" with a short `code` (bash),
  plus "which command…" and concept questions. 2–4 options, plausible distractors.
- **Vary the position of the right answer** (no more than half at index 0) — the quiz does not
  shuffle.
- Spaces in code spans are meaningful (`M  file` vs ` M file`); keep them exact.
- Takeaways: what the lesson and its quiz taught, one sentence each.

## 6. Verify (all of it, every time)

From the repo root:

```sh
pnpm content:run <technology>/<id>   # records session.json + output.txt
pnpm content:check                   # syllabus, ids, staleness, quiz/takeaways shape
```

- Run `content:run` twice: `session.json` must not change (determinism).
- Read `output.txt` against the text: every claim about the output is true.
- Verify **every quiz answer** in a scratch sandbox (in the scratchpad, never in the repo) with
  an isolated config: `HOME=<scratch> GIT_CONFIG_NOSYSTEM=1`, `git config --global` for name,
  email, `core.autocrlf false`, `init.defaultBranch main`.
- `pnpm build`, then look at `/<technology>/<id>/` at 1440px and at a real 390px width.
  Headless Chrome on Windows has a minimum window width, so a 390px screenshot is cropped and
  looks broken: load the page in a `<iframe style="width:390px">` on a temporary page instead
  (and delete that page from `dist/` afterwards).
- `pnpm lint && pnpm format:check && pnpm check`.

## 7. Batch phase

Module by module, in syllabus order. Lessons of one module may be written by parallel subagents,
each given the brief (section 2), this file and the exemplars; Claude then reads every lesson,
re-runs section 6 and fixes inconsistencies (terms, spelling, context overlap). An independent
reviewer agent (given the files, not Claude's conclusions) is worth it for the first modules.

## 8. Hand-off

- Tell the user, in Azerbaijani, what each lesson teaches, its context, and what was verified;
  ask for a review of tone and clarity. Do not mark lessons done in docs/ROADMAP.md before that.
- Add a docs/HISTORY.md entry and update docs/ROADMAP.md.
- Commit on a content branch: `feat(content): add the <technology> <module> lessons`; one PR
  per module (the user's rule: module PRs).
